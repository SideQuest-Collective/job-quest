# Contract `jq-interview/1`

This file is identical in `SideQuest-Collective/job-quest` and `SideQuest-Collective/interview-copilot`. Change both copies in the same pair of pull requests. Each side reads the major version from `jq-interview/<major>` and refuses a different major with a one-line message. Either tool works fully when the other is not installed.

## Discovery

| Side | Sees the other when | Override |
|---|---|---|
| Job Quest | `~/.interview/app/capture.py` exists | `INTERVIEW_HOME` (default `~/.interview`) |
| /interview | `~/.job-quest/bin/jq` is executable | `JOB_QUEST_HOME` (default `~/.job-quest`) |

`jq` here is Job Quest's command-line tool, not the JSON processor of the same name. Job Quest installs it as a symlink in `~/.job-quest/bin`, which is never added to `PATH`. /interview always runs it by absolute path: `"${JOB_QUEST_HOME:-$HOME/.job-quest}/bin/jq"`.

`jq` is the only entry point /interview uses. Neither side reads the other's internal data files except the session folder (outbound) and the inbound files listed below.

## `jq` CLI (Job Quest)

Every subcommand prints one JSON value on stdout. On failure it exits non-zero and prints `{"error": "<one line>"}`. It does not need the Job Quest dashboard to be running.

| Command | Output |
|---|---|
| `jq version` | `{"version": "<semver>", "contract": "jq-interview/1"}` |
| `jq roles --company <name>` or `jq roles --all` | `[{"roleKey", "company", "role", "stage", "hasWorkbook", "hasTailoredResume"}]` |
| `jq interview-context <roleKey> [--round <round>] [--no-agent]` | `{"written": [path], "skipped": [{"path", "reason", "wroteInstead"?}], "cheatsheet": path or null, "practice": path or null}` |
| `jq ingest-session <folder>` | `{"status": "ingested" or "unchanged" or "unlinked", "folder", "effects": {"timeline": [], "stage": {"from", "to"} or null, "workbookQids": [], "tasks": [], "progress": []}, "summary": "<one line>"}` |
| `jq link-session <folder> <roleKey>` | same shape as `ingest-session` |

- `roleKey` is `"Company|Role"`. `<round>` is one of `coding`, `system`, `behavioral`, `recruiter`, `screen`. `<folder>` is a folder name under `~/.interview/sessions/` or an absolute path to one.
- `roles --company` matches the company case-insensitively: the company's slug equals the query's slug, or starts with it followed by a word break (`two` matches `Two Sigma`). `roles --all` lists every tracked, saved, or applied role across companies, including roles without an application. The two flags are mutually exclusive. Both forms return the same fields, ordered by most recent tracker activity first, then role key.
- `interview-context` never blocks on building a workbook. When the role has none, it writes what it can and lists the gap under `skipped` with reason `no-workbook`. `cheatsheet` is the cheat-sheet path /interview should load (the target path whenever a file exists there); `practice` is the practice file Job Quest wrote, if any. `--no-agent` uses only cached cheat sheets.

## Inbound files (Job Quest writes into `~/.interview/`)

| Path | Content |
|---|---|
| `context/resume.md` | the master resume rendered to markdown |
| `context/<company>-jd.md` | the role's job description, level, location, posting URL |
| `context/target.md` | profile answers (location, level, timeline, values), compensation (or "decide a number before the call"), tracker notes including memory from earlier recruiter calls |
| `cheatsheets/<company>.json` | `{"_generatedBy": "job-quest", "contract": "jq-interview/1", "roleKey", "workbookId", "cards": [{"title", "category", "bullets", "code"?}]}`; categories `intro, algorithms, probability, fundamentals, infra, design, critique, warmup`; 4 to 6 bullets per card; at most 40 cards; at most 240 characters per bullet |
| `practice/<roleId>.json` | practice set, below |

`<company>` is the company slug (lowercase ASCII, words joined by `-`). `<roleId>` is the slug of company plus role.

Practice set:

```json
{ "_generatedBy": "job-quest", "contract": "jq-interview/1", "roleKey": "", "workbookId": "",
  "round": "system", "questions": [ { "qid": "", "prompt": "", "type": "open", "rubric": "", "answer": "", "choices": [] } ] }
```

Ownership marker. Markdown files Job Quest writes start with this exact first line:

```
<!-- generated by job-quest (jq-interview/1); edits are overwritten -->
```

JSON files carry `"_generatedBy": "job-quest"` at the top level. Job Quest overwrites a target only when it carries the marker or does not exist. Otherwise it writes `<name>.jq.<ext>` beside it (for example `cheatsheets/acme.jq.json`) and reports the target under `skipped` with reason `user-owned`.

## Session tagging (/interview side)

```
capture.py daemon <round> [--role <roleKey>] [--practice <file>]
capture.py practice-results [folder]        # stdin: [{"qid", "grade", "note"}]
```

`session.json` fields added by this contract:

| Field | Type | Meaning |
|---|---|---|
| `contractVersion` | `"jq-interview/1"` | present on every session written by a contract-aware /interview |
| `roleKey` | string or null | the Job Quest role this session belongs to |
| `practiceSet` | absolute path or null | the practice file used; non-null means a practice session |
| `practiceResults` | `[{"qid", "grade": "got" or "partial" or "missed", "note"}]` | practice grades; `[]` otherwise |
| `practiceQuestions` | list | the loaded practice questions, for the HUD |
| `endedAt` | epoch seconds | when capture stopped |

The /interview skill asks the user to confirm AI assistance is allowed before anything else; this contract does not change that rule.

## Outbound (session folder, read by Job Quest)

Job Quest reads `session.json`, `debrief.md`, `stages.md`, `transcript.jsonl`, and `transcript.md` from `~/.interview/sessions/<folder>/`. Required: `session.json` with `round` and `questions`. Markdown sections are optional. Sessions without `contractVersion` are accepted read-only and treated as unlinked until the user links them in Job Quest. Job Quest never writes into `~/.interview/sessions/`.

## Versioning

Adding an optional field or an optional flag keeps the major. Removing or renaming a field, command, or flag, or changing what one means, bumps the major in both repositories.
